Same style as "Game of Chocolates" — this is another game theory problem, and the winning move here is to brute-force small values of `n` first, look for a pattern, then verify it. Let's carefully set up the rules first, since this one has a few tricky terminal conditions worth nailing down before writing any code.

**Step 1: Understand every way the game can end.**

From a number `x`, a player can either:
- Divide `x` by `2, 3, 4,` or `5` (floor the result), or
- Subtract `2, 3, 4,` or `5` from `x` (only valid if the result stays `≥ 0`).

Three special things happen:
- **If a move produces `1`**, the player who *just moved* automatically loses — right away, no more turns matter.
- **If a move produces `0`**, the game ends there. The *next* player has no valid move (you can't divide `0` into anything new, and subtracting would go negative), so that next player loses — meaning the player who moved to `0` wins.
- **If a player genuinely has no valid move at all** (rare, but worth keeping in mind for very small numbers), that player loses too.

**Step 2: Classify every number the same way we did for the chocolates game.**

A number `x` (for `x ≥ 2`, since `0` and `1` are special/terminal) is a **winning position** if the player to move can find *some* move landing on `0` (immediate win) or landing on a **losing position** for the opponent. It's a **losing position** if *every* available move either lands on `1` (auto-loss for the mover) or lands on a winning position for the opponent.

**Step 3: Brute-force small values before guessing any pattern.**

Let's build a table for small `n` by simulating this recursively, exactly like we did with the chocolates game.

- **If your move turns the number into exactly `1`** — bad news for you — you automatically lose, right there, game over, no more moves happen.

The question asks: given the *starting* number `n`, and assuming **both players play as cleverly as possible** (nobody makes a silly mistake), who wins — Jon or Arya?

**2. Real-life example**

Think of it like a "hot potato" countdown game with a poison number. You and a friend take turns shrinking a pile of `n` coins — either splitting it into a smaller pile by dividing, or removing a few coins directly. If you're the one who leaves *exactly* `1` coin in the pile, you instantly lose the game (that `1` coin is "poisoned"). If you manage to remove the very last coin (leaving `0`), you win instantly, since your friend has literally nothing left to touch on their turn.

**3. Real-world use case**

This is a classic **combinatorial game theory** setup — the same style of reasoning used in Nim, coin games, and the Wythoff's game from your chocolates problem. These "who wins with optimal play" problems train a very transferable skill: reducing a complicated set of rules down to a simple "winning position vs losing position" table, which is exactly the kind of thinking used in real algorithmic game AI (like move evaluation in chess engines, at a conceptual level) and in analyzing strategic resource-allocation problems.

**Tying back to the simple version:** it's the same hot-potato game — for a given starting pile size, we want to know whether the *first* player (Jon) has some clever sequence of divides/subtracts that guarantees the *second* player (Arya) eventually gets stuck at `1` or `0` before Jon does, no matter how well Arya defends.

## Q: how are you getting the table

Let's walk through exactly what that code did, step by step — no magic, just brute-force simulation.

**The function, again:**
```python
@lru_cache(maxsize=None)
def wins(x):
    moves = []
    for d in [2,3,4,5]:
        moves.append(x // d)
    for s in [2,3,4,5]:
        if x - s >= 0:
            moves.append(x - s)

    if not moves:
        return False

    for y in moves:
        if y == 1:
            continue
        if y == 0:
            return True
        if not wins(y):
            return True

    return False
```

**Step 1: `moves` — list every place `x` could go.**

For a given `x`, this builds the list of every number reachable in one move: `x//2, x//3, x//4, x//5` (the four divisions), plus `x-2, x-3, x-4, x-5` (the four subtractions, only kept if they don't go negative). That's up to 8 candidate next-numbers.

**Example: `x=6`.** Divisions: `6//2=3, 6//3=2, 6//4=1, 6//5=1`. Subtractions: `6-2=4, 6-3=3, 6-4=2, 6-5=1`. So `moves = [3, 2, 1, 1, 4, 3, 2, 1]`.

**Step 2: for each possible next-number `y`, decide if THIS move wins for the current player.**

- **`if y == 1: continue`** — moving to `1` is an auto-loss for whoever just moved, so this particular move is never something the current player would pick to win with — skip it, check other moves.
- **`if y == 0: return True`** — if some move lands exactly on `0`, that move instantly wins (the opponent gets stuck with no move). Since the current player just needs **one** winning move to be considered a "winning position," we can stop right there and return `True`.
- **`if not wins(y): return True`** — this is the recursive heart: "go find out (by calling `wins` on this smaller number `y`) whether *the opponent*, standing at `y`, would win or lose." If the opponent would **lose** from `y` (`not wins(y)` is `True`), then moving there is a winning choice for the current player — return `True` immediately.

**Step 3: if none of the moves worked, it's a loss.**

If we tried every single candidate `y` in `moves` and never hit a `return True`, that means every option either forced an auto-loss (`y==1`) or handed the opponent a winning position. So the current player has no good move at all — `return False`.

**Step 4: `@lru_cache` avoids recomputing the same thing over and over.**

Since `wins(y)` might get called many times for the same `y` from different callers (e.g., both `x=6` and `x=8` might both want to check `wins(3)`), the cache remembers previously computed answers instead of redoing the recursion — this is what actually makes the brute force fast enough to run for hundreds of values instead of taking forever.

**Step 5: how the "table" (list of losing positions) got built.**

```python
losing = []
for n in range(2, 300):
    if not wins(n):
        losing.append(n)
```

This just calls `wins(n)` for every `n` from `2` to `299`, one at a time, and collects the ones where `wins(n)` came back `False` — meaning "Arya wins" (since Jon, who always moves first, would be the loser at those numbers). That collected list is exactly what printed as `[6, 7, 16, 17, 40, ...]`.

**Tying it together:** nothing clever was "found" — the code just mechanically re-simulates the entire game tree from every number down to `0`/`1`, using recursion + caching to make it efficient, and then we visually scanned the resulting list for patterns (which, as we saw, turned out to be irregular, telling us to switch strategy to direct bottom-up DP instead of a formula).

## Q: Okay recursion?

Let's connect the dots — what we just did by hand **is** recursion, just done manually. Let's build up the concept properly.

**1. Simple explanation**

Recursion is when the answer to a question depends on the answer to a *smaller version of the exact same question* — and you keep shrinking the question until it becomes so small that you already know the answer without needing to ask anyone else.

That's exactly what we did: to know "can I win from `6`?", we needed to know "can I win from `2`?", "can I win from `3`?", "can I win from `4`?" — smaller versions of the *same* question. And to know those, we eventually needed "can I win from `0`?" — which we just *know* directly (no, you can't, there's no move). That "no more asking, I just know" point is called the **base case**.

**2. Real-life example**

Imagine you're in a line of people, and you want to know "how many people are ahead of me?" You could count the whole line yourself — or you could just ask the person directly in front of you: "how many people are ahead of *you*?" That person asks the person in front of *them* the same exact question, and so on, all the way to the very first person in line, who says "zero, I'm first" (the base case — no one to ask). Then that answer travels back down the line, each person adding `1` to what they heard, until it reaches you. Everyone asked the *exact same question*, just to a smaller and smaller version of the line.

**3. Real-world use case**

Recursion is the natural fit for anything that's built from smaller copies of itself: folder structures (a folder contains files and other folders, which contain more files and folders...), search trees, and — exactly like here — games where "the best move from position X" depends on "the best move from every position you could reach next." It's also how you'd naturally compute things like factorials, Fibonacci numbers, or explore a maze.

**4. Technical deep dive — tying it to what we hand-computed**

What we did by hand:
- `0 → NO` (base case — no move possible, just *know* this directly)
- `2 → YES` (because one of its moves reaches `0`, which is an instant win)
- `3 → YES` (same reasoning)
- `6 → NO` (because *every* move from `6` leads to a `YES` — a place where the opponent, not you, gets to win)

In code, "asking the same question about a smaller number" becomes a function calling *itself* with a smaller input:

```python
def wins(x):
    # base case: if x has no legal moves, you lose
    if x == 0:
        return False  # (this get handled naturally by the moves list being checked)

    for y in all_the_places_you_could_move_to(x):
        if y == 1:
            continue  # bad move, skip
        if y == 0:
            return True  # instant win
        if not wins(y):   # <-- this is the "recursion": asking the same question about y
            return True   # opponent can't win from y, so you win by moving there

    return False
```

The line `if not wins(y):` is the recursive call — the function `wins` is calling *itself*, just with a smaller number `y` instead of `x`. This mirrors exactly what we did on paper: to answer for `6`, we needed the already-known answers for `2, 3, 4` — and those answers, in turn, were built from `0`'s answer.

**Tying back to the simple version:** recursion is just formalizing "ask the same question about a smaller case, and stop asking once you reach a case you already know" — which is precisely the "keep asking about the person in front of you until you hit the front of the line" idea, and precisely what we did filling in `0, 2, 3, 4, 5, 6` one at a time by hand.

Let's turn what we did by hand into a loop — filling in a table from left to right, instead of a function calling itself.

**The key fact that makes this safe:** every move from `x` (dividing or subtracting `2,3,4,5`) always lands on a number **smaller than `x`**. So if we fill in the table in order — `0, 2, 3, 4, 5, 6, ...` — then by the time we reach `x`, **every number `x` could possibly move to has already been filled in.** No guessing, no forward references needed.

**The code:**

```python
def playersWinner(n):
    dp = [False] * (n + 1)   # dp[x] = True means "the player to move at x can win"
    # dp[0] stays False — no legal move from 0, so whoever's turn it is loses

    for x in range(2, n + 1):   # fill the table left to right, x=1 is never a real state we sit at
        moves = [x//2, x//3, x//4, x//5]
        for s in [2, 3, 4, 5]:
            if x - s >= 0:
                moves.append(x - s)

        can_win = False
        for y in moves:
            if y == 1:
                continue          # moving to 1 is an auto-loss, not a usable move
            if y == 0:
                can_win = True    # instant win, opponent stuck at 0
                break
            if not dp[y]:         # opponent lands on a number they can't win from
                can_win = True
                break

        dp[x] = can_win

    return "Jon" if dp[n] else "Arya"
```

**Line-by-line, matching what we did on paper:**

- `dp = [False] * (n+1)` — this is our whole "table," one slot per number from `0` to `n`. Starts all `False` (we'll overwrite as we compute).
- `for x in range(2, n+1)` — this is us walking through `2, 3, 4, 5, 6, ...`, exactly the order we filled the table by hand.
- `moves = [...]` — same 8 candidate next-numbers we listed by hand for `6` (`3,2,1,1,4,3,2,1`).
- `if y == 1: continue` — same as us saying "bad move, skip."
- `if y == 0: can_win = True` — same as us saying "instant win."
- `if not dp[y]: can_win = True` — this is the recursion, but *without* actually calling a function again — since `dp[y]` was **already computed** in an earlier loop iteration (because `y < x` always), we just **look it up directly** instead of recursing.
- `dp[x] = can_win` — store the final answer for `x`, so future iterations (bigger numbers) can look *it* up too.

This produces the exact same table we built by hand (`0→NO, 2→YES, 3→YES, 4→YES, 5→YES, 6→NO`), just automated and extended all the way to `n`.

## Q: But the question mentions o(n) but it will be o(n^2)

Good instinct to double-check this — but it actually stays `O(n)`, not `O(n²)`. Let's see exactly why.

**The reason it feels like it might be `O(n²)`:** we have an outer loop `for x in range(2, n+1)` — that's `n` iterations — and *inside* it, there's another loop `for y in moves`. When you see "loop inside a loop," it's natural to expect `O(n) × O(n) = O(n²)`.

**But here's the key difference:** the *inner* loop isn't looping over something that grows with `n`. Look at how `moves` is built:

```python
moves = [x//2, x//3, x//4, x//5]
for s in [2, 3, 4, 5]:
    if x - s >= 0:
        moves.append(x - s)
```

No matter how big `x` is — whether it's `6` or `100000` — `moves` **always has at most 8 entries** (4 divisions + at most 4 subtractions). It's not "loop from `0` to `x`" or anything that scales with `x`. It's a **fixed, constant-size list**, always capped at 8, regardless of `n`.

**So the real cost is:** `n` outer iterations × (at most 8) inner iterations = `n × 8` total operations. In Big-O terms, constants get dropped — `n × 8` simplifies to just `O(n)`, not `O(n²)`.

**Compare this to what *would* actually be `O(n²)`:** if the inner loop were something like `for y in range(x)` (checking *every* number smaller than `x`, not just the fixed 8 possible moves), then the total work would be `1+2+3+...+n ≈ n²/2`, which really is `O(n²)`. That's not what's happening here — the game's rules themselves only ever offer **exactly 8 possible moves** at any number, so the inner loop is bounded by that small constant, not by `x` or `n`.

**One-line summary:** "loop inside a loop" only becomes `O(n²)` when the *size* of the inner loop also grows with `n`. Here, the inner loop's size is fixed at `8` forever — so it's `O(n)` overall, with a small constant factor that Big-O notation ignores.

## Q: So x is my move and y is opponent move?

Close, but let's fix the wording — `x` and `y` aren't "my move" and "opponent's move." They're both just **numbers (states)**, and what changes between them is **whose turn it is**, not who "owns" the number.

**More accurate way to say it:**

- `x` is the number **you** are currently facing — it's **your turn** when the number is `x`.
- You pick a move (divide or subtract), and that move **turns `x` into some `y`**.
- The instant that happens, it becomes **your opponent's turn**, and *they* are now the one facing `y`.

So `y` isn't "the opponent's move" — `y` is **the number your move produced**, and now the opponent is the one who has to deal with it. The "move" is the action (divide/subtract) that transforms `x` into `y`; `x` and `y` themselves are just two different game states, one before your move, one after.

**Why this distinction matters for understanding `dp[y]`:** since it's now the opponent's turn at `y`, asking "`dp[y] = ?`" is really asking **"can the opponent win from here?"** — not "can I win by landing here." That's exactly why we check `not dp[y]` — we want to know if the opponent is **stuck** (can't win) at the number we just handed them.

**One more subtlety:** `x` isn't fixed as "always my turn" in some permanent sense either — it just means "whoever's turn it is right now, when the number happens to be `x`." If later the *opponent* ends up facing a state that also happens to equal, say, `4`, then `dp[4]` still applies to *them* the same way — the table doesn't care about Jon vs Arya specifically, it only cares about the number and "can the person facing this number win."
